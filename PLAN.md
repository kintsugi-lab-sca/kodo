# Plan: Plane-cmux Bridge ("kōdō")

## Context

A lightweight system connecting Plane CE (kanban at tasks.kintsugi-lab.com) with Claude Code sessions running in cmux. We tried Operator and agtx — too much framework, too little freedom. What we need:

1. **Kanban = Plane** (already exists: web, mobile, filters, labels)
2. **Runtime = cmux** (each task = a workspace with a colour and a name)
3. **Bridge = lightweight script** (webhooks + cmux CLI + Plane API)
4. **Orchestrator = Claude Code session** with the Plane MCP + the cmux skill
5. **GSD keeps working** inside each session, as always

## Project name

`kodo` (心動 — "heartbeat" in Japanese). Simple, short, easy to type.

## Tech Stack

- **Node.js** — aligned with Claude Code's hook ecosystem (GSD already uses JS)
- **No heavy framework** — only minimal libs (Node's native http, no Express)
- **Own CLI** — `kodo` as the main command
- **Repo on GitHub** — `deikka/kodo`

## Architecture

**Event-driven via Tailscale**: Plane CE and the Mac are on the same Tailscale network.
Plane webhooks reach the Mac directly, with no tunnels or relays.

## Components

### 1. `kodo server` — the heart (event-driven)

**File**: `src/server.js`

An HTTP server (Node's native http, no Express) that:
- Listens on `:9090` for Plane webhooks (via Tailscale)
- Receives POST `/webhook` with the `issue.update` event
- Verifies the HMAC-SHA256 signature (`X-Plane-Signature`)
- If the work item moved to "In Progress" → creates a cmux workspace + launches Claude
- If a session finished (via the Stop hook) → updates Plane to "Done" or "In Review"
- Exposes GET `/status` to see active sessions (JSON)

**Plane webhook configuration**:
- URL: `http://<mac-tailscale-ip>:9090/webhook`
- Events: Issue (create, update)
- Secret: generated by Plane, stored in the `PLANE_WEBHOOK_SECRET` env var

**State store**: `~/.kodo/state.json`
```json
{
  "sessions": {
    "plane-work-item-uuid": {
      "workspace_ref": "workspace:3",
      "session_id": "claude-session-abc",
      "plane_id": "uuid",
      "plane_identifier": "KL-42",
      "summary": "Implement auth",
      "status": "running",
      "started_at": "2026-04-06T18:00:00Z",
      "project_path": "/Users/alex/dev/klab/tenderio"
    }
  }
}
```

### 2. `kodo hooks` — Claude Code <-> kodo

**Files**: `src/hooks/session-start.js`, `src/hooks/stop.js`

**SessionStart hook**:
- Reads stdin (session_id, cwd)
- Looks up state.json to see whether this cwd corresponds to a Plane task
- If it does → injects context: "You are working on KL-42: Implement auth"
- Creates a cmux notification

**Stop hook**:
- Reads stdin (session_id)
- Looks up the session in state.json
- Updates Plane: PATCH work item → state "Done" or "In Review"
- Updates the cmux workspace colour (green = done)
- Removes it from state.json

### 3. `kodo cli` — manual commands

**File**: `src/cli.js` (entry point `bin/kodo`)

```bash
kodo start              # Starts the webhook server (:9090)
kodo stop               # Stops the server
kodo status             # Shows active sessions
kodo launch KL-42       # Manually launches a Plane work item
kodo config             # Configures API key, workspace, projects
kodo orchestrate        # Launches the orchestrating session
```

### 4. `kodo orchestrator` — the brain (Claude Code session)

**File**: `src/orchestrator/prompt.md`

A Claude Code session launched on demand (not permanent) with:
- **Plane MCP server** registered → can read/create/update work items
- **cmux skill** → can create workspaces, read screens, send commands
- **Access to state.json** → knows which sessions are running

It is invoked when:
- `kodo orchestrate` is run manually
- The server detects a situation that requires judgement (session stuck >30min, several tasks competing for priority, a complex task needing decomposition)

The orchestrator's prompt:
```markdown
You are kodo's orchestrator. Your job is to:

1. Review the tasks in Plane (via MCP) and decide priorities
2. Check the state of active sessions (via cmux read-screen)
3. Unblock stuck sessions (send messages via cmux send)
4. Break complex tasks into Plane subtasks
5. Decide when to launch new sessions and when to wait

Rules:
- At most 3 concurrent sessions (cost control)
- Use Sonnet by default, Opus only for complex tasks
- If a session has been idle >30min, investigate and decide: nudge, kill, or escalate
- Update Plane with comments about progress
- When done, signal [kodo:idle] and wait
```

## Full flow (example)

1. **In Plane**: you move "KL-42: Implement auth in tenderio" to "In Progress"
2. **The Plane webhook** reaches the kodo server via Tailscale
3. **kodo server** runs:
   ```bash
   cmux new-workspace --name "KL-42: Auth tenderio" --cwd /Users/alex/dev/klab/tenderio
   cmux workspace-action --action set-color --color Amber
   cmux send --workspace workspace:N "claude --session-id kodo-KL-42 'Implement authentication...'"
   ```
4. **Claude starts** → the SessionStart hook injects the Plane context
5. **Claude works** (it can use /gsd:* if the project has GSD)
6. **Claude finishes** → the Stop hook fires:
   - PATCH the Plane work item → "Done"
   - `cmux workspace-action --action set-color --color Green`
   - Removes the session from state.json
7. **cmux notification**: "KL-42 completed"

## Orchestrator flow

1. `kodo orchestrate` or an automatic trigger
2. Creates the cmux workspace "kodo-orchestrator" (colour Indigo)
3. Launches Claude with the Plane MCP + state.json context
4. The orchestrator:
   - Reads tasks from Plane → "there are 3 in Doing, 2 in Todo"
   - Checks the screens of active sessions via cmux
   - Makes decisions: "KL-55 has been idle 40min, I'll send it a nudge"
   - `cmux send --workspace workspace:5 "Do you need help? The goal is..."`
   - Updates comments in Plane
5. When there are no more actions → signals idle and finishes

## Plane project -> local path mapping

In config or in a mapping file `~/.kodo/projects.json`:
```json
{
  "plane-project-uuid-tenderio": "/Users/alex/dev/klab/tenderio",
  "plane-project-uuid-fvf": "/Users/alex/dev/roman/fvf"
}
```
Configured once with `kodo config` and reused.

## Phased implementation

### Phase 1: Skeleton + Plane client + cmux client (MVP)
- `kodo config` — interactive setup
- `kodo launch KL-42` — manually launch a task
- Plane API client (list states, list work items, update work item)
- cmux client (new-workspace, send, read-screen, workspace-action)
- Basic state store

### Phase 2: Webhook server + hooks
- `kodo start` / `kodo stop` — HTTP server for Plane webhooks
- HMAC-SHA256 signature verification
- Claude Code hooks (session-start, stop)
- Automatic reaction to state changes in Plane
- `kodo status` — see active sessions

### Phase 3: Health checks + notifications
- Idle/stuck/error detection
- cmux notifications
- Automatic colours per state

### Phase 4: Orchestrator
- `kodo orchestrate` — Claude session with the Plane MCP
- Orchestrator prompt with decision rules
- Automatic trigger when there are stuck sessions

### Phase 5: Polish
- Interactive `kodo config` — a wizard that lists projects, asks for paths, validates that they exist
- `kodo install` — installs hooks and the MCP server automatically
- Tests
- README
- npm publish (optional)
